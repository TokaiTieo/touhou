东方异变录 · 稳定性备忘录：超时/心跳/判活机制现状与风险
记录日期：2026-08-19(v0.12.0,V7 存档)
来源：全项目排查(backend/、js/、desktop_launcher.py),仅记录事实与风险,未改动任何代码。

================================================================
一、结论摘要
================================================================
项目已有多层有限超时设计,"模型慢/断流/断连/进程崩溃"四类常见
故障均能有限等待后报错或自动恢复,不会无限阻塞。

唯一会真正无限阻塞的场景:后端进程/事件循环整体假死。
该场景目前没有任何心跳或看门狗覆盖,用户端表现为永久转圈,
只能手动杀进程重启。

================================================================
二、已有机制清单(层层兜底,勿重复建设)
================================================================
1. AI HTTP 调用:60s connect/read 超时;最多 4 次重试 + 跨模型
   fallback。—— backend/services/ai_service.py:25,172,265
2. 流式读取:60s 无新 chunk 即超时。—— ai_service.py:368-380
3. asyncio 兜底:wait_for 65s 必返回(模型线程仍可能在后台跑)。
   —— ai_service.py:476-485
4. LangGraph 任务:task 75s / entrypoint 95s 上限。
   —— backend/services/turn_workflow.py:114-136
5. 回合去重:同 turn_id 的 SSE/重试/断线重连共享同一在途任务;
   asyncio.shield 保证断连不取消后端回合。
   —— backend/services/turn_coordinator.py:59-102
6. 主动取消:停止按钮 → task.cancel() + checkpoint 清理。
   —— turn_coordinator.py:148-164;backend/routes/ghost.py:949-962
7. 前端断线恢复:fetch 抛错 → 轮询回合状态(90s 硬上限)→
   同 turn_id 重发,幂等不重复结算。—— js/api.js:229-261
8. 崩溃恢复:进程 crash 后 checkpoint 持久化,同 turn_id 重发
   自动断点续跑。—— turn_workflow.py:393-410
9. 桌面端启动期判活:60s 探测(可配 TOUHOU_STARTUP_TIMEOUT),
   超时则报错退出并写 logs/startup-diagnostics.json。
   —— backend/desktop_launcher.py:61-71
10. checkpoint SQLite:busy_timeout=5000;库损坏自动隔离重建。
    —— turn_workflow.py:154,174-225

三、场景矩阵:hang 了会怎样
================================================================
[OK] 模型无响应/超时
     60s 超时 → 重试(≤4 次)→ 跨模型 fallback → 返回失败文案;
     asyncio 层 65s 先行截断。有限等待后报错,不丢状态。

[OK] 模型"滴水式"慢输出(一直有 chunk)
     读超时不触发,但 65s wait_for + 95s entrypoint 兜底。有限等待。

[OK] SSE 中途断流(TCP 断开/页面刷新)
     前端 catch → 轮询恢复(≤90s)→ 同 turn_id 重发;shield 保证
     后端回合继续。自动恢复,幂等不重复结算。

[注意] SSE 假死(连接在、永远无数据)
     前端 reader.read() 无读超时,不会主动进入恢复;依赖后端
     65/95s 超时后主动推 error/done 结束流来解套。有限等待,
     但前端不会出现"正在恢复"提示。

[OK] 回合锁持有者 hang
     锁内最重操作被 65/95s 限定;异常/取消经 async with 必释放。
     不会永久持锁;但锁获取本身无超时(理论性单点)。

[OK] 后端进程 crash
     checkpoint + 回合收据持久化;重发同 turn_id 自动恢复或取回
     结果。可自动恢复。

[风险] 后端进程假死(事件循环/GIL 卡死)
     uvicorn 无请求超时;桌面端启动后无运行期看门狗;前端普通
     fetch 全无超时(本机 TCP 不会 RST)→ 所有请求永久挂起。
     无限阻塞,需手动杀进程重启。

[OK] checkpoint SQLite 锁竞争/损坏
     busy_timeout 5s 后报错 → 回退直连生成;损坏库自动隔离重建。

================================================================
四、风险点清单(按严重度排序)
================================================================
R1 [高] 进程级假死零检测
     - js/api.js:28 apiCall() 裸 fetch,无 AbortController/无超时
     - backend/desktop_launcher.py:181 "healthy" 之后无任何心跳
     - uvicorn 启动未设任何超时参数(backend/api.py:95)
     后果:事件循环一旦卡死,用户端永久转圈,只能手动重启。

R2 [中] SSE 无心跳
     - backend/routes/ghost.py:207-214 只在有 token/result 时 yield
     - js/api.js:97-104 reader.read() 无读超时
     后果:长生成期间连接静默,经代理/安全软件可能被断流;
     假死连接前端无法主动发现。

R3 [中] wait_for 超时后 executor 线程不可回收
     - ai_service.py:476-485,Python 无法杀线程
     后果:幽灵线程最坏存活 4×模型数×60s;持续超时场景默认线程池
     (min(32, cpu+4))可能耗尽,之后 AI 调用排队失败(但 wait_for
     仍 65s 返回,不无限阻塞)。

R4 [低] 锁获取无超时
     - turn_coordinator.py:111 asyncio.Lock
     - backend/world_manager.py:50-52 threading.RLock
     后果:当前靠 AI 层超时兜底不会永久持有;未来若在锁内新增
     无超时阻塞调用,会变成该角色回合的永久死锁。

================================================================
五、修复建议(备忘,未实施)
================================================================
建议最小方案(两项即可覆盖最大风险 R1):

1. 桌面端运行期心跳:backend/desktop_launcher.py 在服务启动后
   起一个守护线程,每 30s 探测 /api/health,连续 3 次失败则
   自动重启服务线程(或至少弹窗提示用户重启)。

2. 前端 apiCall 加超时:js/api.js 引入 AbortController,
   普通请求 30s、状态轮询 10s 超时;超时后按"断线"进入既有
   恢复流程(复用 waitForTurnResult 逻辑,不新增状态机)。

可选增强:
3. SSE 心跳:后端事件流每 15s 无数据时 yield 一行 ": ping"
   (SSE 注释行,前端天然忽略),前端 reader 加 45s 读超时。
4. 回合锁获取加超时(如 120s),超时返回 409 并提示稍后再试。
